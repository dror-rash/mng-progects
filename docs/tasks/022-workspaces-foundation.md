# Task 022: Workspaces own the data (M8 step 1)

- **Status:** in-progress
- **Milestone:** M8
- **Zone / package:** `packages/db`, `apps/dashboard`
- **Feature file:** `docs/features/workspaces.feature`
- **ADR:** `docs/adr/0005-workspaces-and-authorization.md`

## Why
ADR-0005: workspaces, not individual users, own projects, tasks and customers. This step moves the data and every access check onto workspaces, with no visible change for someone working alone, so later steps can add members, invites and assignees.

## Scope
- Schema: `workspace` (id, name, created_at); `workspace_member` (workspace_id, user_id, role `admin`/`member`, joined_at; primary key on both); required `workspace_id` on `project` and `organization` (cascade delete), indexed. `owner_id` stays as "created by".
- Migration: one personal workspace per existing user ("<name>'s workspace", the user as admin); every project and customer moves into its owner's workspace; then `workspace_id` becomes required.
- New users get a personal workspace the first time they open the dashboard.
- Current workspace: the `workspace` cookie if the user is a member of it, otherwise their oldest membership. The header shows its name.
- One access rule: a record is visible only to members of its workspace. Pages and actions use membership helpers instead of owner checks. Lists, counts and "create" use the current workspace. Linking a project or task to a customer requires the customer to be in the same workspace.

## Out of scope
- Members page, roles UI, invite links (023); switcher and creating workspaces (024); assignees and "My tasks" (025).

## Acceptance criteria
- [ ] A new account sees its personal workspace's name in the header.
- [ ] Everything that worked before still works for a single user (full suite green).
- [ ] Another workspace's projects, tasks and customers stay hidden (existing cross-user scenarios, now cross-workspace).

## Approach (brief)
`features/workspaces/` with `currentWorkspaceId(memberships, cookie)` (pure, unit-tested), `requireWorkspace(path)` for pages, `requireWorkspaceForAction()` for actions, and membership-joined record lookups. Migration generated by drizzle-kit, then edited (before it is applied) to backfill before adding NOT NULL.
