# Task 026: M8 review fixes

- **Status:** in-progress
- **Milestone:** M8
- **Zone / package:** `packages/db`, `apps/dashboard`, `e2e`
- **Feature files:** `docs/features/workspace-members.feature`, `docs/features/workspace-switching.feature`, `docs/features/task-assignees.feature`, `docs/features/customer-links.feature`, `docs/features/task-details.feature`
- **ADR:** `docs/adr/0005-workspaces-and-authorization.md`

## Why
The `/venice-review` of M8 (tasks 022–025) found one critical access bug, two races/mix-ups in membership changes, a cascade that would delete shared work, and tests that pass for the wrong reason. They need fixing before M8 merges.

## Scope
- **Removed stays removed.** `ensurePersonalWorkspace` only adds the user to `personal-<id>` when it creates that workspace now (or a concurrent first request just did). If it already exists without them (they left or were removed), they get a new workspace instead of being re-added as admin.
- **Last admin under concurrency.** Changing a role, removing a member and leaving run in one transaction that locks the workspace row, so two admins can't both pass the "keeps an admin" check. The membership change and clearing assignments happen in that same transaction. Changing or removing someone who isn't a member says so instead of silently succeeding.
- **Actions act on the workspace the page showed.** Members-page actions, leaving, and the create forms (project, customer) post a hidden `workspaceId`; the server checks membership (and role for admin actions) for that id. The cookie only picks the default for pages.
- **Admin check shows an error.** Creating an invite link as a non-admin returns "Only admins can manage this workspace" on the form.
- **Creator column.** `project.owner_id` and `organization.owner_id` become nullable with `ON DELETE SET NULL` (migration 0015), so deleting a user can't delete shared work.
- **Creating a workspace** inserts the workspace and its admin in one transaction.
- **Tests that pass for the wrong reason:** "Removing a member clears their assignments" checks the board (which reads the assignee directly); the outside-assignee step uses a real user from another workspace; the "Current" badge check looks at the right row.
- **Missing tests:** role change, cross-workspace access with real ids (switching to a workspace I'm not in, a forged workspace cookie, another user's task id in my form, a customer from my other workspace), and a record link opened from another of my workspaces.

## Out of scope
See the parking lot: everything the review rated minor and not listed above.

## Acceptance criteria
- [ ] Someone removed from their first workspace stays removed after reloading.
- [ ] Two admins removing each other at the same time leave one admin.
- [ ] A members page left open acts on the workspace it shows, even after switching in another tab.
- [ ] A member can't create invite links by changing the form.
- [ ] An admin can make a teammate an admin.
- [ ] I can't switch to a workspace I'm not in; a forged workspace cookie shows only my own work.
- [ ] Another user's task id in my task form changes nothing; a customer from my other workspace can't be linked to a project.
- [ ] A project link works from any of my workspaces.
- [ ] Deleting a user keeps the projects and customers they created.

## Approach (brief)
- `requireWorkspaceForAction(formData)` reads the posted `workspaceId` and returns that membership (or throws). `requireAdmin` builds on it.
- `changeMembership(workspaceId, { userId, role | null })` locks the workspace row (`SELECT … FOR UPDATE`), re-reads its members inside the transaction, applies `keepsAnAdmin`, writes, and clears assignments when someone leaves.
- Migration 0015 is generated by drizzle-kit from the schema change.

## Rollout note
Migration 0012 makes `workspace_id` required before the M8 code is live. During a deploy (CI migrates, then builds and rolls out) the old revision can't create projects or customers for a few minutes, and the shared preview database breaks create forms on other open PRs still on pre-M8 code. Accepted: no other app PRs are open and there are no production users yet. For later schema changes like this, split into expand (nullable + backfill) and contract (NOT NULL) migrations.
